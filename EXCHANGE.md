# Биржа с портфельными заявками: дизайн, формулы, архитектура

Документ к `pfx_exchange.py`.

---

## 1. Что представляет собой эта биржа

Биржа котирует `n` активов. **Валюты и денежные остатки — такие же активы**, отдельной сущности «деньги» в модели нет. Ни один актив не является привилегированным.

Внутреннее состояние — вектор логарифмов цен `S ∈ R^n`. Цены `P = exp(S)`.

Книга заявок определяет только **отношения** цен. Общий уровень фиксируется отдельной калибровочной конвенцией и на динамику не влияет.

Заявка — это не лимитная заявка в стакане. Это **гладкая кривая спроса на портфель**: агент объявляет пропорции, курс безразличия и агрессивность, а движок непрерывно находит цену, при которой все такие кривые балансируются.

---

## 2. Примитив заявки

Заявка — тройка `(w, z, λ)`.

### 2.1 `w` — веса по стоимости

Словарь `актив → доля стоимости`, с обязательным условием

```
Σ_i w_i = 0
```

Это **условие самофинансирования**: сколько стоимости пришло, столько ушло. Денежная нога — обычная координата вектора.

| Смысл | `w` |
|---|---|
| Купить X1 за рубли | `{X1: +1, RUB: -1}` |
| Базис между площадками | `{X1: +1, X2: -1}` |
| Корзина 60/40 за доллары | `{A: +0.6, B: +0.4, USD: -1}` |
| Купить Y, продав X пополам с кэшем | `{Y: +1, X: -0.5, RUB: -0.5}` |

`w` безразмерен. Он несёт одновременно две вещи:

* пропорции сделки по стоимости;
* вектор эластичностей заявки (см. §3.2).

### 2.2 `z` — курс безразличия

Цена портфеля определяется как **геометрический индекс**

```
Π(P) = Π_i P_i^{w_i}
```

Так как `Σ w_i = 0`, индекс `Π` инвариантен к умножению всех цен на константу — это чистое **отношение** цен, а не абсолютная величина.

* для `{X1:+1, RUB:-1}` → `Π = P_X1 / P_RUB` = цена X1 в рублях;
* для `{X1:+1, X2:-1}` → `Π = P_X1 / P_X2` = базис площадок.

`z > 0` — уровень `Π`, при котором заявка не торгует. **`z` не зависит ни от какого выбора базового актива.**

### 2.3 `λ` — агрессивность

Размерность: **деньги / время**. Это единственное место в заявке, где вообще появляются деньги.

Читается как «сколько нотионала в единицу времени на единицу логарифмического мисприсинга». Так как мисприсинг измеряется в относительных единицах, `λ` сопоставим между активами любого масштаба цены.

## 3. Динамика заявки

### 3.1 Сигнал

```
f = log(z) − w·S
```

Безразмерен. Вблизи точки безразличия `f ≈ (z − Π)/Π`, то есть это относительная дешевизна портфеля. `f > 0` → покупать, `f < 0` → продавать.

Нотионал торгуется со скоростью

```
v̇ = λ f          [деньги / время]
```

За шаг `Δt` торгуется `V = λ f Δt`. Разложение по ногам:

```
стоимость в актив i:   V · w_i
количество актива i:   Δn_i = V · w_i / P_i
```

Так как `Σ w_i = 0`, сумма стоимостных ног равна нулю **точно**, при любых ценах. Кэш списывается и зачисляется автоматически, отдельной бухгалтерии для денег не нужно.

### 3.2 Эластичность

```
∂f / ∂ log P_i = − w_i
```

Чувствительность заявки к процентному движению каждой цены **постоянна** и равна весу. Заявка не меняет своей формы по мере движения рынка.

(В линейной шкале аналогичная производная равна `−w_i P_i`, то есть заявка молча переформатируется при движении цен.)

### 3.3 Композиция заявок

Заявки образуют линейное пространство: `w` складываются, `log z` складываются, то есть `z` перемножаются.

```
{X:+1, RUB:−1} @ z_X    минус    {Y:+1, RUB:−1} @ z_Y
                      =
{X:+1, Y:−1}   @ z_X/z_Y
```

Треугольная согласованность встроена в формализм. Кросс-инструменты не требуют отдельной логики: котировка X1/RUB и X2/RUB автоматически задаёт согласованный базис X1/X2.

## 4. Клиринг

### 4.1 Условие равновесия

Чистый поток стоимости в каждый актив равен нулю:

```
Σ_a λ_a f_a w_{a,i} = 0     для каждого i
```

Поскольку `P_i > 0`, это эквивалентно нулевому потоку в **количествах** — та же система, другой множитель.

### 4.2 Линейная система

Подстановка `f_a = log z_a − w_a·S` даёт

```
A S = b

A = Σ_a λ_a w_a w_aᵀ        (n×n, симметричная, PSD)
b = Σ_a λ_a log(z_a) w_a
```

Одно решение линейной системы на шаг. Число заявок влияет только на сборку `A` (разреженно, `O(m·k²)`, где `k` — число ног в заявке); стоимость решения — `O(n³)` по числу **активов**, а их десятки.

### 4.3 Вариационная форма

```
S* = argmin_S  Σ_a λ_a ( w_a·S − log z_a )²
```

Равновесная цена — **взвешенный МНК-консенсус котировок**, то есть взвешенное геометрическое среднее по `z`. Каждая заявка — гиперплоскость `w_a·S = log z_a` в пространстве логарифмов цен, `λ_a` — её жёсткость, равновесие — взвешенная проекция.

**Проверка**: две встречные заявки на один инструмент с равными `λ` и уровнями 105 и 95 дают `√(105·95) = 99.8749`. Одна заявка без встречной даёт `f = 0` и нулевой поток — торговать не с кем.

### 4.4 Калибровка

Так как `Σ_i w_{a,i} = 0` для всех заявок, то `A·1 = 0` и `1ᵀb = 0`. Система всегда совместна, но решение определено с точностью до `S → S + c·1`, то есть **до общего множителя на все цены**.

Это направление и есть выбор численера. Фиксируется одним линейным ограничением

```
π·S = g
```

где `π` — актив или корзина, `g = log(заданная цена)`. Требование: `Σ π_i ≠ 0`, иначе `π` не пересекает свободное направление.

**Единица счёта совпадает с калибровкой.** Прибив `P_RUB = 1`, мы одновременно (а) зафиксировали уровень цен и (б) объявили, что `λ`, нотионалы и переоценка выражены в рублях. Это одна и та же конвенция, не две.

### 4.5 Вырожденность

Если по активу на этом шаге нет заявок, соответствующие строка и столбец `A` нулевые и цена не определена. Добавляется тихоновская регуляризация к предыдущему состоянию:

```
(A + εI) S = b + ε S_prev
```

Там, где заявки говорят что-то определённое, при малом `ε` решение почти не меняется; там, где молчат, получается ровно `S_prev`.

В логарифмах это означает «цена осталась той же» в **относительном** смысле. В линейной шкале та же добавка тянула бы цену на абсолютную величину и на дешёвом активе могла бы утащить её за ноль.

`ε` масштабируется внутри движка как `ridge · tr(A)/n`, поэтому параметр `ridge` безразмерен.

**Ридж не самофинансируем.** Регуляризация `εI` соответствует набору фиктивных заявок с `w = e_i`, у которых `Σ w ≠ 0`. Поэтому при `ridge > 0` потоки заявок не сходятся к нулю точно — остаётся невязка `ε(S − S_prev) + μπ`. Эту невязку принимает на себя **счёт биржи** (`house_account`, по умолчанию `__house__`), и тогда сохранение количеств выполняется **точно**. Размер этого счёта — прямая мера того, насколько сильно регуляризация искажает книгу: если он растёт, ридж великоват или книга слишком тонкая.

При `ridge = 0` невязка равна машинному нулю и счёт биржи не двигается.

### 4.6 Итоговая численная схема

Всё вместе — KKT-система размера `(n+1)`:

```
[ A + εI   π ] [ S  ]   [ b + ε·S_prev ]
[   πᵀ     0 ] [ μ  ] = [      g       ]
```

Множитель `μ` равен нулю, когда книга согласована с калибровкой (что верно всегда при `Σ w = 0`), поэтому он служит диагностикой. Невязка условия клиринга равна `ε(S − S_prev) + μπ` и на практике имеет порядок `1e-10` от валового нотионала.

## 5. Размерности

| Объект | Размерность | Зависит от численера? |
|---|---|---|
| `w` | безразмерно | нет |
| `z` | отношение цен | нет |
| `f` | безразмерно | нет |
| `S`, `A`, `b` | безразмерно | только через калибровку |
| `λ` | деньги / время | **да** (масштабный множитель) |
| нотионал `V` | деньги | **да** |
| балансы `n_i` | физические единицы | нет |
| P&L | деньги | **да** (валюта отчёта) |

Ключевое: денежная размерность локализована в `λ` и в бухгалтерии. Уравнения равновесия от неё полностью свободны.

Если агент хочет котировать `λ` в своей валюте, а не в единице счёта, движок конвертирует по цене **предыдущего** шага (`lam_ccy`). Это явный лаг в один шаг, который сохраняет клиринг точным линейным решением; без него множитель `e^{S_ccy}` сделал бы систему нелинейной.

## 6. Почему логарифмическая шкала

Краткая сводка того, что даёт `f = log z − w·S` вместо `f = z − w·P`.

1. **Свободное направление имеет правильный смысл.** При `Σ w = 0` линейное правило инвариантно к `P → P + c·1`, то есть не различает цены (1, 2) и (101, 102) — бессмыслица. Логарифмическое инвариантно к `P → c·P`, то есть не различает (1, 2) и (10, 20) — это просто деноминация, и она действительно не должна ничего менять.

2. **Смена базового актива — смена базиса, а не пересчёт модели.** Для любого `k`, благодаря `Σ w_i = 0`:
   ```
   w·S = Σ_i w_i (S_i − S_k) = Σ_{i≠k} w_i log(P_i / P_k)
   ```
   Те же коэффициенты `w_i`, то же `z`. В линейном правиле смена базы делит интенсивность на `P_k` и переносит уровень безразличия с `z` на `z/P_k` — обе величины эндогенны и бегают во времени.

3. **Положительность бесплатно.** `P = exp(S) > 0` всегда. Линейная система по `P` при тонкой книге вполне может вернуть отрицательные цены.

4. **Симметрия направлений.** Мера отклонения — отношение, поэтому «вдвое дороже» и «вдвое дешевле» штрафуются одинаково. Арифметическая версия смещает равновесие вверх.

5. **Обращение заявки точное.** Заявка «купить Y за X» с курсом `z` — это ровно та же заявка с `w → −w`, `z → 1/z`, и её `f` меняет знак без каких-либо поправок. В линейном правиле обратная заявка даёт `f(P) ∝ (1 − zP)/P²` — гипербола, совпадающая с исходной только локально.

6. **Численно то же самое.** Задача остаётся линейной системой того же размера. Логарифмы ничего не стоят.

Цена вопроса: индекс портфеля становится геометрическим, `Π = Π P_i^{w_i}`, а не арифметическим. Это корзина с постоянными **весами** (непрерывно ребалансируемая), а не с постоянным **количеством** бумаг. Для заявки, описанной в терминах пропорций, это скорее более точная семантика, но её надо понимать.

## 7. Архитектура программы

### 7.1 Слои

```
        ┌───────────────────────────────────────────┐
        │  участники                                 │
        │  Order(weights, z, lam, ...)               │
        │  цены и количества, обычная шкала          │
        └────────────────┬──────────────────────────┘
                         │  submit / cancel / deposit
        ┌────────────────▼──────────────────────────┐
        │  граница: Exchange.submit                  │
        │  валидация Σw = 0, z > 0, активы           │
        │  log(z) — здесь и только здесь             │
        └────────────────┬──────────────────────────┘
        ┌────────────────▼──────────────────────────┐
        │  ЯДРО (только логарифмы)                   │
        │  _effective_lambdas  — лаг-1 конверсии,    │
        │                        лимиты, экспирации  │
        │  _solve              — KKT, ридж, калибр.  │
        └────────────────┬──────────────────────────┘
        ┌────────────────▼──────────────────────────┐
        │  граница: step()                           │
        │  P = exp(S) — здесь и только здесь         │
        │  V = λ f Δt,  Δn_i = V w_i / P_i           │
        └────────────────┬──────────────────────────┘
        ┌────────────────▼──────────────────────────┐
        │  учёт: balances[agent][asset], физ. едини- │
        │  цы; ClearingReport в обычной шкале        │
        └───────────────────────────────────────────┘
```

**Инвариант, который держит всё:** `log` и `exp` от цены вызываются ровно в четырёх местах — при приёме заявки (`log z`), при инициализации (`log P₀`), при выдаче цен (`exp S`) и при конверсии `lam_ccy`. Больше нигде в кодовой базе логарифмов от цен нет. Пока это правило соблюдается, запутаться в шкалах негде.

### 7.2 Разделение спецификации и состояния

* `Order` — **frozen dataclass**, неизменяемая спецификация от участника.
* `_LiveOrder` — внутренняя обёртка: плотный вектор `w`, `log z`, флаг активности, израсходованный бюджет.

Участник никогда не видит `_LiveOrder`, движок никогда не мутирует `Order`. Расширение формата заявки — это добавление поля в `Order` и его обработка в `_effective_lambdas`.

### 7.3 Что делает шаг

1. `_select(dt)` — отбор активных заявок, снятие экспирированных, конверсия `lam_ccy` по **предыдущим** ценам.
2. `_tighten(orders, lams, S, dt)` — снижение `λ` под ограничения `max_rate` и `max_notional`, вычисленные при ценах `S`. Только вниз, поэтому повторное применение сходится.
3. Цикл: `_tighten` по старым ценам → `_solve` → `_tighten` по новым ценам → повтор, пока ограничения не перестанут связывать (обычно 1–2 итерации, потолок 8). Число использованных итераций попадает в отчёт как `cap_iterations`.
4. `_solve` — сборка `A`, `b`, решение KKT-системы, получение `S*` и `μ`.
5. `step` — вычисление `f`, `V`, разложение по ногам, конверсия в количества, зачисление на балансы, передача невязки на счёт биржи, списание бюджетов, формирование отчёта.

**Почему лимиты применяются до клиринга, а не после.** Обрезать уже посчитанный филл нельзя: это оставит книгу несбалансированной, потоки перестанут сходиться к нулю, и невязка вылезет в счёт биржи как настоящая утечка. Снижение `λ` до решения сохраняет условие клиринга точным. Цена — итерации, но их одна-две, и каждая стоит одно решение системы размера `n+1`.

### 7.4 Публичный интерфейс

```python
ex = Exchange(assets=[...], prices={...}, unit_of_account="RUB")

oid = ex.submit(Order(weights={"X1": +1, "RUB": -1}, z=105.0, lam=2e6, agent="a"))
ex.cancel(oid)
ex.deposit("a", "RUB", 1e7)

rep = ex.step(dt=1.0)
rep.prices              # {asset: price}
rep.fills               # [Fill(order_id, agent, f, notional, quantities)]
rep.net_quantity_flow   # поток по заявкам, ~0 по каждому активу
rep.house_flow          # то, что добрал счёт биржи; сумма с предыдущим = 0 точно
rep.max_value_imbalance # невязка клиринга, сравнивать с rep.gross_notional
rep.cap_iterations      # сколько раз пришлось поджимать lambda

ex.price("X1")
ex.rate({"X1": +1, "X2": -1})     # любой кросс-курс напрямую
ex.mark_to_market("a")
```

`rate()` заслуживает отдельного упоминания: он принимает произвольный `w` и возвращает уровень соответствующего геометрического индекса. Это универсальный выход «в обычную шкалу» для внешних площадок — любой кросс, любой базис, любая корзина, без выбора базового актива.

### 7.5 Точки расширения

| Что | Куда |
|---|---|
| Новые поля заявки | `Order` + `_effective_lambdas` |
| Комиссии | множитель на `V` в `step`, либо мёртвая зона по `f` (см. §8) |
| Односторонние заявки | `_solve` → активные ограничения (см. §8) |
| Приоритеты / очереди | `_effective_lambdas`, порядок и веса `λ` |
| Логирование, метрики | `ClearingReport` |
| Инвентарные лимиты | проверка `balances` в `_tighten` |

## 8. Свойства и ограничения

### Что работает хорошо

* **Единственность и устойчивость.** `A` положительно полуопределена по построению, равновесие единственно с точностью до калибровки, решение точное и не итеративное.
* **Положительность цен** гарантирована структурой.
* **Отсутствие базового актива.** Выбор численера остался только в отчётности.
* **Мультиплощадочность даром.** `X1` и `X2` — отдельные координаты; базис — это `w = {X1:+1, X2:−1}`, читается напрямую, отдельного механизма не требует.
* **Скорость.** Одно решение системы `(n+1)×(n+1)` на шаг. Число заявок в стоимость решения не входит.
* **Естественная семантика «нет контрагента».** Единственная заявка на некое направление получает `f = 0` и не торгует.

### Что нужно понимать

* **Это не стакан.** Нет очереди, нет приоритета цена-время, нет бид-аска, нет дискретного матчинга. Микроструктурные эффекты (динамика спреда, позиция в очереди, adverse selection через филлы) в этой модели не воспроизводятся. Это гидродинамический предел торговли, а не имитация биржевого движка.

* **Заявка двусторонняя.** `{X1:+1, RUB:−1}` с `z = 105` покупает ниже 105 **и продаёт выше 105**. Это котировка маркет-мейкера вокруг `z`, а не лимитная заявка на покупку. Для односторонних заявок нужно `f = max(0, log z − w·S)`, что превращает клиринг из линейной системы в выпуклую кусочно-квадратичную задачу — решается активными ограничениями за несколько итераций, но линейность теряется. Если это нужно, лучше закладывать сразу.

* **Инвентарных ограничений нет.** Балансы могут уходить в произвольный минус: движок не проверяет, есть ли у агента деньги. Дисциплина — на стороне агентов (снимать заявки, двигать `z`) или через `max_notional`. При необходимости жёсткого лимита проверку надо ставить в `_effective_lambdas`, где она снизит `λ` до клиринга и сохранит согласованность.

* **`λ·Δt` — главная ручка.** Прирост позиций пропорционален `λ f Δt`. Прайсинг не имеет проблем жёсткости (цена — мгновенное равновесие книги, не интеграл), но балансы интегрируются явной схемой, поэтому слишком крупный шаг даёт перелёт. Ориентир: `λ Δt` должно быть заметно меньше типичного объёма книги.

* **Трение отсутствует.** Нет спреда, комиссий, проскальзывания. Спред можно ввести мёртвой зоной `f = sign·max(0, |log z − w·S| − θ)`, но, как и односторонние заявки, это делает задачу кусочно-линейной.

* **Ридж — это не «ничего».** При очень тонкой книге регуляризация заметно тянет цену к предыдущей. Смотреть на `gross_notional` и `max_value_imbalance`: если их отношение заметно больше `1e-8`, ридж работает сильнее, чем задумано.

### Когда этот дизайн — правильный выбор

Когда интересует **формирование цены** из совокупного спроса множества агентов с портфельными предпочтениями: равновесная динамика, кросс-эффекты между активами, арбитраж между площадками, обратная связь «цена → P&L → поведение». Здесь дизайн даёт точное, быстрое и численно надёжное решение.

Когда интересует **микроструктура** — исполнение, очередь, спред, тиковая динамика, — нужен полноценный стакан, и эта модель не заменит его.

Код возврата 0 при полном прохождении, 1 иначе.

### Два сорта тестов

**Аналитические** — привязка равновесия к замкнутой форме. Именно они говорят, что реализована та модель, которая задумана:

| Тест | Что закреплено |
|---|---|
| `two_quotes_equal_size` | равные `λ` → `√(z₁z₂)` |
| `two_quotes_weighted` | неравные `λ` → взвешенное геометрическое среднее |
| `single_order_does_not_trade` | без контрагента `f = 0` |
| `basket_order_prices_the_index` | трёхногая корзина выводит свой индекс на `z` |
| `numeraire_invariance` | одна книга в рублях и в долларах → одинаковые отношения цен |
| `order_reversal_is_the_same_order` | `(w, z)` и `(−w, 1/z)` — одна и та же сделка |
| `triangular_consistency` | котировки X/RUB и Y/RUB задают кросс X/Y |
| `gauge_choice_does_not_move_ratios` | калибровка на корзине вместо актива ничего не меняет |

**Структурные инварианты** — свойства, обязанные выполняться после любого шага любой книги. Упакованы в `check_step` и `check_conservation`, поэтому подключаются к своим сценариям бесплатно:

1. цены конечны и строго положительны;
2. калибровка держится: единица счёта стоит ровно `unit_price`;
3. каждый филл самофинансируем — стоимость ног суммируется в ноль;
4. рынок клирится: невязка мала относительно валового нотионала (при `ridge = 0` — до машинной точности);
5. заявки плюс счёт биржи дают ровно нулевой суммарный поток;
6. количества согласованы со стоимостями;
7. ничего не создаётся и не уничтожается за произвольное число шагов.

### Как добавить свой тест

```python
@test("mygroup")
def t_my_thing():
    "однострочное описание, показывается раннером"
    ex = build(["RUB", "X"], {"RUB": 1.0, "X": 100.0},
               [({"X": +1, "RUB": -1}, 105.0, 1e6, "buyer"),
                ({"X": +1, "RUB": -1}, 95.0,  1e6, "seller")])
    rep = ex.step(1.0)
    check_step(ex, rep)
    eq_rel(rep.prices["X"], 99.87492, rtol=1e-5, label="X")
```

Функция регистрируется декоратором автоматически. Тест считается пройденным, если не бросил исключение. Хелперы: `eq_rel`, `near`, `is_true`, `raises`, `check_step`, `check_conservation`, `build`, `totals`, `gmean`.

`build` по умолчанию ставит `ridge = 0`, чтобы аналитические тесты сравнивались с точным равновесием. Если в сценарии есть некотируемый актив, задавай `ridge=1e-9`, иначе система вырождена.

### Что тесты уже поймали

Три настоящих дефекта, все исправлены в движке:

* потоки не сходились к нулю при `ridge > 0` — регуляризация не самофинансируема, невязка теперь идёт на счёт биржи;
* `max_notional` перебирал бюджет на несколько процентов, потому что `λ` ограничивалась по мисприсингу предыдущего шага — добавлено поджатие итерациями;
* ожидание в тесте инвариантности численера само было неверным: нотионалы масштабируются ровно на `1/90`, а количества — на отношение расклиренного курса к предполагаемому, поскольку `λ` несёт денежную размерность.
